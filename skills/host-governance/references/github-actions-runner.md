# GitHub Actions Self-Hosted Runner

Use this reference for host-owned installation and lifecycle of a GitHub
Actions self-hosted runner. Keep repository workflow intent in the consuming
project, and keep the runner account, installation path, service, exposure, and
runtime ownership in host governance.

## Linux installation contract

Run the runner under a dedicated unprivileged user named `actions`. Do not run
`config.sh` with `sudo`, as root, or by setting `RUNNER_ALLOW_RUNASROOT`. Use
`/opt/actions-runner` as the installation directory; do not install under
`/root`, because the service user cannot safely traverse the root home.

Create the account and installation directory as root before downloading or
configuring the runner:

```bash
id actions >/dev/null 2>&1 || useradd --create-home --shell /bin/bash actions
install -d -o actions -g actions /opt/actions-runner
```

Switch to the runner identity, enter the fixed directory, and use the current
download, integrity-check, and registration instructions generated by the
target repository or organization in GitHub. Treat the registration token as a
short-lived secret and never persist it in Git, documentation, or logs.

```bash
su - actions
cd /opt/actions-runner
./config.sh --url <repository-or-organization-url> --token <registration-token>
```

After `config.sh` succeeds, leave the `actions` shell. As root, enter the same
directory and install the background service explicitly for `actions`:

```bash
exit
cd /opt/actions-runner
./svc.sh install actions
./svc.sh start
./svc.sh status
```

When connected through a non-root administrative account, run the three
`svc.sh` commands with `sudo` instead. Root privilege is for service
installation and control, not runner registration or job execution.

## Verification and safety

- Verify the runner appears online at the intended repository, organization,
  and runner group before routing production jobs to it.
- Run a bounded manual smoke workflow using the runner's exact custom label.
- Do not open an inbound listener merely to make the runner connect; the runner
  initiates its control connection to GitHub over outbound HTTPS.
- Do not grant `actions` passwordless sudo, Docker socket access, signing keys,
  or production credentials unless the authorized workflow explicitly needs
  them and the added privilege has a separate recovery and review path.
- Treat the work directory as persistent and potentially contaminated by prior
  jobs. Do not schedule untrusted public-repository or fork code on a
  long-lived host runner.
- Keep automatic runner updates enabled unless a separately owned update and
  compatibility process exists.

To remove a registered runner, stop and uninstall its service first, then run
`config.sh remove` as `actions` with a new removal token. Deleting
`/opt/actions-runner` alone does not unregister an already configured runner.
