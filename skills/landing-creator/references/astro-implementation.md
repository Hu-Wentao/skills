# 根据确认文档制作 Astro Landing

在内容确认且用户要求制作页面时读取。让框架服从内容与行动路径，不以脚手架默认模块替代设计决定。

## 1. 确定工程位置与内容版本

- 读取已确认的内容文档及变更记录。核对仓库、工作目录、页面路由、域名、语言与现有发布方式。
- 检查现有 package.json、锁文件、Astro 配置、样式、组件、图片和项目指令；使用项目已有包管理器。
- 现有 Astro 项目增改对应路由；单独 landing 的目录按项目惯例选定。现有非 Astro 主站不自动整体迁移；若无法隔离实现，提出具体位置建议。
- 新项目使用与环境兼容的 Astro 稳定版本及对应官方资料；记录实际版本并锁定依赖。不要写死“最新版”版本号，或为了 landing 升级无关项目。
- 仓库是否公开、商业资料能否提交、托管目标与域名是不同决定。开源产品不自动意味着访谈、客户数据、内部测试材料可以公开；公开项目只保留获准公开的信息与必要引用。

## 2. 从灰度原型进入视觉实现

1. 按确认的真实内容、阅读顺序和 CTA 路径实现手机、桌面灰度页面。根据内容确定断点，不照搬固定区块数。
2. 实现相关导航、表单、弹窗、提交中、成功、失败、取消等状态；不适用的状态无需创建。
3. 执行可开展的理解与路径测试。没有真实目标用户时，记录人工走查或 AI 审查，保留目标用户测试计划。
4. 按反馈回到对应设计步骤；只有影响已确认承诺、条件或路径的变化才需要重新确认。
5. 加入品牌字体、配色、间距、组件样式、图片与有解释作用的动效，生成手机与桌面截图并检查。

遵循 [Astro 项目结构](https://docs.astro.build/en/basics/project-structure/)：页面位于 src/pages；layouts 与 components 承担布局和可复用片段；public 保存直接分发的静态资源。目录分拆以复用需要为准，小页面不必另建通用页面生成器。

默认采用静态输出。普通交互可以使用 Astro 组件中的浏览器脚本，见 [脚本与事件处理](https://docs.astro.build/en/guides/client-side-scripts/)；只有现有组件或交互需求需要时才引入 UI 框架与 hydration。表单可调用已有服务，动态请求确有需要时再选择适配器与服务端渲染，不向静态页虚构后端能力。

## 3. 保持内容、素材与行动一致

- 将确认文案逐项映射到组件。可用小型类型化数据文件集中管理可见文案，但不要把内部证据表、访谈原话或未授权资料打包给浏览器。
- 保留确认的导航和辅助入口；主 CTA 的文字、URL、权限、费用与结果和文档一致。外部链接不得虚构为内部可完成流程。
- 产品演示优先真实截图或实际输出。概念图或模拟示例注明性质；不生成假评价、客户墙、指标截图。
- 图片设置尺寸、合适裁切与替代文字；装饰图不重复朗读。视频或复杂效果应有静态替代；首屏信息不能依赖动画播放完成。
- 外部表单或产品链路有实际成功响应才展示对应成功状态；错误、重复提交、取消及不可用时有反馈。不要用任意等待时间模拟提交成功。
- 链接、下载、注册、支付等验证优先使用预览/测试环境；记录只能验证到哪一步，不为验证制造真实订单或发送真实申请。
- 无后台接收能力时写明缺口，在用户确认调整后使用真实可用的替代入口；不能静默把“开始使用”改成“联系我”。

## 4. SEO、可访问性与指标

- 按已确认语言设置 lang、标题、描述；有真实域名后配置 canonical 与分享元数据。需要索引时按部署条件处理 robots、sitemap；预览与生产的索引策略分别记录。
- 使用语义化标题与区域、明确链接文本、表单标签和可关联的错误提示；支持键盘导航、可见焦点、合理顺序和减少动效偏好。
- 检查手机触控、放大/重排、文本与背景对比及非颜色状态提示。不要仅因自动检查通过就声称全面符合某个标准。
- 仅接入项目已有或已获授权的分析服务；没有服务时可准备事件接口与事件定义，并明确“尚未采集”。
- 事件区分展示、CTA 点击、提交尝试、提交成功与产品结果；产品结果必须由可靠的实际行为确认。避免敏感输入和表单内容进入分析事件。
- 跨域跳转只证明离开 landing，不能自行推算对方注册、购买或产品激活。记录归因、去重、时间窗口与数据覆盖缺口。

## 5. 验证与交付

读取项目现有 scripts 并运行相应检查。按 [Astro CLI](https://docs.astro.build/en/reference/cli-reference/) 的职责区分诊断、生产构建和本地预览：执行项目类型检查（通常包含 astro check）及 build；再检查构建产物的 preview。缺失检查依赖时使用与项目版本兼容的工具，未执行须说明。preview 用于验收，不作为生产服务器。

| 范围 | 需要实际检查的内容 | 记录 |
| --- | --- | --- |
| 内容 | 文案、价格、限制、素材和确认版本一致；无未填写占位内容 | 文档版本、差异 |
| 页面 | 窄屏与宽屏、长内容、截图可读、无意外横向溢出 | 视口、截图、问题 |
| 操作 | 导航、锚点、CTA、相关表单及状态、键盘和焦点 | 实际到达节点 |
| 工程 | 类型检查、构建、运行错误、失败请求、静态资源和路由 | 命令、结果 |
| 性能 | 主要图片与脚本体积、加载稳定性、必要的测量 | 工具、设备条件，不能预填分数 |
| 交付 | 元数据、生产域名/路径、索引策略、指标事件及授权范围 | 已验证与缺口 |

检查力度匹配实际风险；不要为纯文案或样式改动建立镜像实现的测试套件。没有可用浏览器时继续完成构建和代码检查，列出未完成的视觉/交互验收；不能声称已截图或已经通过。

回填内容文档的实施结果与未验证事项，提供代码位置、预览地址、截图和已运行命令。发布仅按当前授权和项目流程执行；部署后检查实际页面和链路才能报告上线。没有真实流量数据时只交付测量方案。
