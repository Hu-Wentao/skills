# 修订 Landing：扫描、方案与实施

用于已有页面的扫描、审查、诊断、优化或修订。复用 13 步设计标准，以当前页面和产品证据为起点；不把每次扫描重新变成完整的新建访谈。

## 1. 确定本轮范围与基线

- “扫描／检查／审查／评估”默认交付检查结果和修订建议，不修改页面。
- “修复／按确认方案实施”执行已授权的改动；已有确认不重复询问。只补问会改变价值主张、费用、受众、能力或行动路径的缺失决定。
- 记录仓库、分支、提交、工作区改动、页面位置、技术栈、语言和可用的部署版本。源码、未合并工作区与线上版本分别记录，不能互相替代。
- 阅读现有内容文档、产品实现、README、用户明确决定和实际页面。标明哪些是事实、用户陈述、设计决定或待验证假设；“存在于旧页面”不表示“已经用户确认”。
- 保留项目现有框架与部署方式。纯 HTML、Astro 或其他框架均可扫描；未获迁移要求时，不把缺少 Astro 本身列为缺陷。

## 2. 按 13 步检查当前页面

覆盖 13 个设计步骤，但只追问影响结论的缺口。优先检查：

1. 页面任务、主受众和主 CTA 是否清楚；能否从首屏判断产品是什么、适合谁、能完成什么。
2. 页面承诺、命令示例、价格、依赖、支持平台和权限边界是否与实际代码、发布版本及文档一致。
3. 按钮、安装命令、文档入口和产品首次成功之间是否连通；缺失的服务端或真实安装验证不得以代码存在替代。
4. 区块任务是否重复、产品展示是否解释了真实结果、证据是否能支撑承诺。
5. 导航、标签页、复制、表单等已有交互的正常和失败状态，移动端布局、键盘、焦点、减少动效、无 JavaScript 表现及已支持语言。
6. 是否存在内容确认、用户研究、参考页适用理由、真实用户测试和指标定义。缺少这些材料记为“未见证据”，不要断言团队从未做过，也不要伪造用户理解或转化结论。

使用现有检查命令及非破坏性验证。网站不需要构建时，不要求运行无关 CLI 的完整构建。避免为了测试执行登录、授权、付款、安装目标产品或修改生产配置。对无法检查的真实路径明确写出验证边界。

## 3. 形成可审阅的修订方案

按下列结构交付，用户未要求文件时可直接在回复中提供：

- **扫描范围**：源码与部署版本、已执行检查、未执行检查。
- **优先问题**：编号、严重度、观察或假设、证据位置、用户影响、推荐修订、验收方式。
- **13 步覆盖表**：每一步的已有材料、缺口与处理；允许“部分满足／待验证／不适用”，不要用无证据的总分制造精度。
- **保留项**：当前有效的设计及能力边界，避免修订破坏已有正确行为。
- **最小修订顺序**：先处理不实承诺和中断路径，再处理理解与操作问题，最后安排视觉与测量优化。
- **需要确认的决定**：只列真正缺失的产品或内容选择，通常不超过三个。

优先级以用户后果为依据：P0 为核心路径不可用或严重错误承诺；P1 为妨碍理解/开始使用或重要条件遗漏；P2 为次要表达、发现性或验证完善。纯文案判断标为设计判断或假设，未经测试不声称必然提升转化。

涉及其他正在进行的工作时，注明相应工作区和可见改动；未合并、未验证、未部署的修复不标为当前主分支已解决。不要覆盖、合并或清理他人的工作来完成扫描。

## 4. 按确认范围实施

用户确认具体修订或已授权直接修复后，更新受影响的内容决定与实现，保持文案、证据和实际行动一致。用变更对照记录旧内容、新内容、理由和确认依据，无需为了局部修改重填全部新建模板。

需要 Astro 改动时读取 Astro 实施指引；其他现有技术栈使用该项目的检查及预览方式。执行与改动相关的响应式、键盘、链接、交互和产品路径回归；报告未完成的真实用户测试与线上数据验证。内容确认不自动授权部署，沿用当前发布授权。
